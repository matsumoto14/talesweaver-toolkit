# ADR-009: 一般公開・配布

- ステータス: 採用
- 期間: 2026-08-27〜2026-08-31
- 元文書: goals/2026-08-28-public-release.md(git 履歴参照)

## 背景

リポジトリと配布物を外部に出せる状態にし、ユーザーがアプリから匿名で問い合わせを送れて
GitHub Issue になる経路を作る必要があった。あわせて権利表記・CSP・配布 CI・アプリ識別子・
DB バックアップなど、公開前にしか変えられない項目を先に決めた。着手順は
段階4(アプリ整備)→ 段階3(配布)→ 段階5(問い合わせ)とした。

## 決定

- **NOTICE.md で非公式ツールであることと同梱データの出典を明記する**。ゲーム開発元・運営元とは
  無関係であること、Tale Wiki 由来の数値データとアイコン画像の出典、削除要請の窓口(GitHub Issue)を
  1 ファイルにまとめた。アイコン(talewiki 添付由来)は出典・非公式表記を付けて同梱を続け、
  権利者からの申し出があればダウンロード方式へ切り替えられる余地だけ残す(未収録アイコンは
  破線 + `?` で表示されるため、同梱をやめても機能が落ちない設計が既にある)
- **製品名を TW Context、アプリ識別子を `dev.twcontext.app` にする**。識別子は
  `%APPDATA%` の保存先フォルダ名になり、配布後に変えると既存ユーザーのデータが行方不明になるため、
  変更できるのは公開前の今だけと判断した。`tw-context.dev` の逆順だが、Android/iOS の
  パッケージ名がハイフンを許さないため(architecture.md が想定するモバイル展開に備え)ハイフンは外した。
  同じ機会に DB ファイル名も `tw-context.sqlite` に揃え、上部バーの表記も旧称 TW TOOLKIT から
  TW CONTEXT に直した(サービスイン前でデータ変更可というユーザー判断による)
- **配布は GitHub Actions(`tauri-apps/tauri-action`)で `v*` タグ push → 下書き Release**。
  同じビルド成果物を Cloudflare R2 の固定 URL(`dl.tw-context.dev/latest/...`)にもそのまま上げ、
  紹介ページ(`tw-context.dev`、Cloudflare Pages)のダウンロードボタンは R2 を指す。
  Releases 経由では書き換えのたびにページを触る必要が出るため、固定 URL 側を正とし、
  **手で片方だけ差し替えない**(同一ビルドを両方へ上げることだけを「ずれない」担保にする)。
  紹介ページと問い合わせ中継の Worker は別 Cloudflare プロジェクトにし、ページ更新が
  API を落とさないようにした
- **コード署名は公開時点では必須にせず、未設定でも通す**。Azure Trusted Signing の
  signCommand は Secrets(`AZURE_CLIENT_ID` 等)が揃っているときだけ CI に差し込まれ、
  空なら署名ステップを飛ばして未署名でビルドする。署名基盤は用意しておき、初回リリースを
  署名待ちでブロックしない判断。未署名の間は SmartScreen 警告が出るため、紹介ページに
  回避手順を明記して対応する
- **CSP は `csp: null` を撤廃し `'self'` 系(`object-src 'none'` まで)に締める**。
  アプリは自動的な外部通信を持たない設計のため。問い合わせ送信のためだけに
  `connect-src` へ中継サーバーの origin(`https://inquiry.tw-context.dev`)を追加する。
  この URL は配布版の CSP に焼き込まれるため、`workers.dev` ではなく自分のドメインにし、
  あとで向き先を移せるようにした
- **問い合わせは中継サーバー(Cloudflare Workers)経由の匿名投稿にし、ブラウザで GitHub を
  開かせない**。認証は GitHub App(Issues: write のみ、installation token は 1 時間で失効)。
  秘密鍵(`GITHUB_APP_PRIVATE_KEY`)は Worker secret に置くが、**App ID と installation id は
  秘密鍵が無ければ何もできない公開情報なので Variables(vars)で管理し、リポジトリで
  バージョン管理する**。ダッシュボードで手入力する項目を秘密鍵と `NONCE_SECRET` の 2 つだけに
  減らすため。匿名投稿への対策は初版から: HMAC 署名 nonce に基づく proof-of-work(外部依存ゼロ、
  nonce を貯めずに検証だけ KV に短期記録)+ IP ハッシュ単位のレート制限(1 日 5 件、
  IP そのものは保存しない)+ 長さ上限・制御文字除去・`@メンション`/`#issue番号`・コードブロック
  無効化のサニタイズ。Turnstile は WebView で動かすために CSP 緩和が要るため初版では入れず、
  荒らされたら足す
- **DB バックアップは `crates/storage` の責務にする**(SQLite の面倒を見るのは storage、
  desktop は呼ぶだけ)。マイグレーション前に版ごとのコピーを取り直近 3 世代だけ残し、
  開けない原因で対応を分ける: ファイル破損(`PRAGMA quick_check`)は退避してバックアップから
  復元、マイグレーション失敗は戻しても同じ所で落ちるためユーザーのファイルには触らず
  インメモリで起動して保存されない旨を帯で伝える。**起動不能にしないこと**を最優先にした
- **自動更新は R2 の固定 URL を配信元にし、当てるのはユーザーが押したときだけにする**。
  アプリは起動時に `https://dl.tw-context.dev/latest/latest.json` を見るだけで、
  新しい版があってもお知らせタブに出すところで止める(§00 03 押した場所は動かない ―
  作業中に勝手に落として再起動を促さない)。配信元を GitHub Releases ではなく R2 にしたのは、
  紹介ページのダウンロードと経路を 1 本にするため。ただし tauri-action が作る `latest.json` は
  下書き Release の asset を指していて公開まで 404 なので、CI が向き先を
  `dl.tw-context.dev/<タグ>/<インストーラ名>` に差し替えてから `latest/latest.json` に上げる。
  **結果としてタグ push の時点で配信が始まる**(下書きを見てから配りたければ、先に手動実行で
  `dev/<実行番号>/` を通して確かめる)。署名鍵は生成済みで公開鍵は `tauri.conf.json` に入り、
  秘密鍵は Secrets のみ
- **お知らせ(更新内容・これから・既知の不具合)は R2 の JSON を正にし、同じファイルを同梱もする**。
  予定と不具合はアプリの版と関係なく動くので、アプリを出し直さずに直せる必要がある。
  元ファイルは `apps/desktop/src/data/news.json` の 1 つだけで、同梱にもそのまま使い、
  main に push すると CI が形を検査して R2 へ上げる(手で 2 か所を揃えない)。
  取得できない・形が違うときは同梱ぶんを出す(お知らせが白紙になるより古い内容のほうがよい)。
  取得は **WebView の fetch ではなく `tauri-plugin-http`(Rust 側)** で行う。R2 は既定で
  `Access-Control-Allow-Origin` を返さず、WebView から取ると CORS で必ず失敗するため
  (実機で確認済み)。配布先に CORS 設定を要求しないほうを選んだ。許可先は capabilities の
  `http:default` で `https://dl.tw-context.dev/*` だけに縛る(CSP は触らない)

## 却下した選択肢

- 問い合わせをブラウザで GitHub Issue 作成画面に飛ばす方式: 却下。匿名で送れず、
  GitHub アカウントを要求することになる
- 初版から Turnstile を導入: 却下。WebView 内で動かすために CSP を緩めるコストが見合わず、
  PoW + レート制限で様子を見て荒らされたら足す方針にした
- 中継サーバーを `workers.dev` のまま運用: 却下。送信先 URL を配布版の CSP に焼き込む都合上、
  向き先を後で移せるよう自分のドメイン(`inquiry.tw-context.dev`)にした
- コード署名が揃うまでリリースを止める: 却下。署名インフラは用意しつつ、未設定でも
  ワークフローが通る形にして初回リリースをブロックしないことにした
- ダウンロードボタンの飛び先を GitHub Releases に直接: 却下。リリースのたびに紹介ページを
  書き換える必要が出るため、R2 の固定 URL を経由させる
- 自動更新の配信元を GitHub Releases(`releases/latest/download/latest.json`)にする: 却下。
  下書きを公開した瞬間に配信が始まる利点はあるが、配布経路が R2 と 2 本になる。
  ダウンロードと更新で違うファイルを配る余地を残さないほうを採った
- 更新を黙って落として次回起動で当てる: 却下。通信と再起動のタイミングをユーザーが選べない。
  0.x のうちは巻き戻せない変更(DB マイグレーション)が入るため、当てる操作は明示にする
- お知らせを WebView の `fetch` で取り、R2 側に CORS を設定する: 却下。配布先の設定に
  依存すると、バケットを移したときにアプリ側から気づけない(黙って同梱ぶんに落ちる)。
  Rust 側から取れば配信元の設定は要らない
- お知らせを GitHub Releases の本文や CHANGELOG.md の生取り込みで出す: 却下。
  予定・既知の不具合は版に紐づかないので置き場所が無く、CHANGELOG は書式が自由すぎて
  アプリ側の表示(種別バッジ・機能名)に落とせない

## 経緯

- 段階4(NOTICE.md・CHANGELOG.md・README 全面更新・DB バックアップ・CSP・情報パネル)と
  段階3(署名なしで通る配布 CI)を先にまとめて実装し(コミット `e31a892`)、
  段階5(問い合わせ中継)を追って追加した(`505504d` ほか)
- 問い合わせ中継は KV namespace id をリポジトリに入れる判断(`d411580`、秘密情報ではないため)、
  必須シークレット欠落を 503 で理由付きで返す修正(`cfedd69`)、App ID/installation id を
  vars へ移す整理(`8b9577a`)を経て安定させた
- ブランド名決定を受けて識別子変更(`9481335`)→ DB ファイル名とブランド表記の追随(`a7597c1`)
  → 紹介ページと R2 配布の追加(`1e870d6`)→ R2 バケット名の実態合わせ(`cdc4cfe`)→
  手動実行でも R2 経路を検証できるようにする修正(`2b5727d`)の順で配布まわりを仕上げた
- 2026-08-31 に自動更新(`tauri-plugin-updater`)とお知らせ配信を足した。CI は既に
  `includeUpdaterJson: true` と署名鍵の口を持っていたが、**アプリ側の updater が入っておらず
  「新しいバージョンが出ると起動時にお知らせします」が実態と合っていなかった**ため、
  プラグイン導入・お知らせタブからの適用・R2 への `latest.json` 差し替え配信をまとめて入れた
- 手順の現在形は `.github/RELEASE.md`(鍵・Secrets・R2 の設定手順、毎回のリリース手順)と
  `site/README.md`(紹介ページの配置・差し替え手順)を正とする
