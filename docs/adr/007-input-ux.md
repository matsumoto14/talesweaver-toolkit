# ADR-007: 入力 UX

- ステータス: 採用
- 期間: 2026-08-21〜2026-08-26
- 元文書: goals/2026-08-21-ux-guidelines-character-screen.md、goals/2026-08-26-input-issues.md(git 履歴参照)

## 背景

旧リポジトリ(docs/legacy-twtoolkit.md)は素ステ・装備・約 60 項目のバフをセッションごとに手入力させる設計で、使うたびに同じ数値を打ち直す道具になっていた。入力欄は「自由度」ではなく「ユーザーが覚えて再入力しなければならない負債」という反省から、docs/ux-guidelines.md は「原則1: 既知の情報をユーザーに入力させない」を最上位に置き、衝突時の優先順位を「入力させない → 選択にする → 登録から分離する → 構造化する」と定めた。

2026-08-21 時点のキャラ画面はこの原則に反していた。登録フォームが素ステ/覚醒/ペット/ルーン/クラウン/聖物/バフ/調整値の 8 セクションを一度に詰め込み(分離違反)、全セクションが同じ見た目・重みで並び(構造化違反)、素ステを ± Stepper のスライダーで打たせ(選択・自由入力の区別違反)、計算画面には一時的な調整値の経路がなかった(通常操作と例外操作の区別違反)。

2026-08-26 には別の切り口で入力欄 149 件(値 71 / 段階 55 / チップ 14 / ドロップダウン 6 / 自由入力 3)を design-system.html §07 の「入力 5 形態」(自動 → 段階選択 → チップ → ステッパー → 自由入力。上から順に試し、飛ばして下に行かない)に照らして棚卸しした。数値欄 71 件すべてが形態 4(ステッパー: − / ＋ と MAX で動かし、値・上限・進捗・MAX が 1 セルに同居)を飛ばして形態 5(自由入力)で処理されており、§07 の最も強い規則に違反していた。

## 決定

- 登録は「名前 + キャラ種」のみとする。素ステ全種 1・覚醒 0/0・stat_sources 中立値はフロントで組み立てて送り、詳細はキャラ詳細画面で編集する(domain/storage の `NewCharacter` 型は変えない)
- キャラ詳細は「基本」「恒常補正」「常用バフ」「調整値」の 4 グループのアコーディオンにし、要約行を常時表示して一度に 1 グループだけ展開する。未設定のグループは「未設定(中立値で計算)」と明示する
- 保存は自動保持 + 一括保存とする。グループ切替で入力を破棄せず、どのグループの保存ボタンを押してもフォーム全体を送る
- 計算画面に「一時調整」を追加する。キャラデータは変更せず計算リクエストにだけ乗せ、トレースの補正源内訳に「一時調整」として出す
- 数値入力は `ui/StatInput.svelte` 1 部品に統一し、`Stepper.svelte` / `NumberField.svelte` は削除する
- 上限のある数値欄は形態 4(ステッパー)を既定にする: − / ＋ と MAX を常設(MAX は 1 タップで置ける)、値と上限は同じセルに同居、セル底に進捗バー、上限到達は面の色が濃くなる(色相はその欄が属する系統に従う。水色系統は金、ラベンダー系統は濃いラベンダー)
- フィールドは「表示が既定、編集は例外」とする。初期値は常に埋まっており、通常は読み取り表示、入力欄は自動値を上書きする例外操作
- 範囲(上限)は入力欄に常設する。順序があって並べられる有限選択は段階選択(`StepSelect`)に寄せ、素の `<select>` とチェックボックスは 5 形態のどれでもないため使わない

## 却下した選択肢

- 素ステの入力に ± Stepper のスライダーを使う → 廃案。範囲が広い(1–310)値にスライダー + 1 刻みボタンでは目的の値に合わせにくい
- グループ単位の部分保存(PATCH 的な差分更新) → 廃案。`update_character` が全フィールド必須の Rust 側 API と噛み合わず複雑化する。全フィールド常時保持 + 一括保存の方が「切替時に破棄しない」を追加のリセット処理なしに満たせる
- 数値欄の空欄・無効値の blur フォールバック先を `min` にする → 廃案。`min` が負の項目(調整「加算」= -999)で、全選択して打ち直そうとしただけの操作が -999 に化ける実害があった。直前の確定値へフォールバックする形に変更した
- 上限到達を示す色を全欄で金に統一する → 廃案。上限到達は「面が濃くなる」ことで示し、色相はその欄が属する系統(水色/ラベンダー等)に従う。金に統一すると系統の意味(§03)と衝突する
- アビリティ/キャラのような順序のない有限選択をチップ列(段階選択)に降ろす → 却下。規格(§14 保留 E)が明示的に否定している。段階ではないので並べても順序の意味が出ず、1 つしか選べないのに複数選べるように見える
- 監査スクリプトの「12 択以下は段階選択に降ろせる」という判定条件 → 却下。規格より粗い基準だったため、順序の有無で判定するよう直すことにした

## 経緯
- 2026-08-21: docs/ux-guidelines.md の 4 原則に照らしてキャラ画面の違反 4 件を洗い出し、登録の最小化・詳細画面のグループ化・素ステ入力の見直し・一時調整の経路を実装した。素ステは当初 `NumberField`(1–310)に統一する案だったが、同日のキャラ画面 v2 で `StatInput` 1 部品への統合に置き換わった
- 2026-08-21(同日、キャラ画面 v2): ユーザーの実使用フィードバック(入力方式が不統一、調整値の意味が伝わらない)を受け、数値入力を `ui/StatInput.svelte`(ラベル | 数値欄 | range スライダー | MAX ボタン)1 部品に統一し、`Stepper.svelte` / `NumberField.svelte` を削除した。空欄・無効値の blur フォールバックも直前の確定値に修正した
- 2026-08-25: デザインシステム適合ループで、素の `<select>` とチェックボックスが 5 形態のどれでもないことを指摘し、順序があって並べられる有限選択を `StepSelect` に寄せた。「フィールドは表示が既定・編集は例外」「範囲は常設する」を規則として確定した。上限到達色の金/紫の食い違いと、スライダーが 5 形態のどれかは「v4 の実物を見ないと決められない」保留として残した
- 2026-08-26: v4(TW Toolkit Prototype v4.dc.html)のエンチャント欄の実物を確認し、保留 2 件が決着した。v4 に `type="range"` は 0 件で、スライダーは実装の逸脱と判明し削除済みで正しいと確認された。上限到達は「面が濃くなる」ことで示し、色相は系統に従う(金/紫の食い違いは水色系統の欄についての記述として整理)ことも確定した。同じ棚卸しで、数値欄 71 件すべてが形態 4(ステッパー)を飛ばして形態 5(自由入力)で処理されている違反(G)、補正源ごとに数の意味(段階/実値/Lv)が違うのに欄が区別しない違反(A)、「OP を追加」が破線 + チップでなく段階選択の見た目になっている違反(D)、ランダム OP の欄が何の値か言えていない違反(B)を検出し、直す順序を G → A → D → B → 規格の更新 → 監査スクリプト修正の順に決めた。ドロップダウン 6 件(アビリティ/キャラ/主軸スキル)と上限の実態確認(装備補正 1,000 など)は決定待ちのまま残した
- 2026-09-01: 計算タブの「計算の材料」に**地力**(装備ではなく育てて上がるもの)のカードを 3 つ足した —
  覚醒・エタの意志 / シャープネスビジョン / ソウルリンク 5〜7。効きが大きいのにキャラタブでしか
  触れず、「盛ったらどこまで届くか」を計算タブで試せなかったため。入力形はキャラタブと同じ
  (節目の段 + 数値)にそろえ、変更は試し変更(sim)として扱う(保存しない)。差分チップも
  `awakening` / `sharpness` / `soul_link` の 3 つを新設した。
  実装中に、シャープネスビジョンの Lv 段と補助チップ(「1〜4」「未習得」)を同じ行に置くと、
  段が 10 個に増えたときチップが段の上に重なって押せなくなることを実機で検出し、行を分けた
  (§09 規則 3)。段の数で消える補助チップは、消さずに `disabled` にして幅を固定した(§09 規則 4)
- 2026-09-01: 装備ペイン先頭の「基本 / 強化」表が「壊滅的にわかりづらい」というユーザー指摘。
  原因は、灰色の小さい散文 1 塊に 4 つの別々の事実(基本に何が入る / 強化に何が入る /
  強化倍率 / テシスコアだけ入らない)を詰め、**そもそもなぜ 2 行あるのか**を一度も
  言っていなかったこと。事実を説明する対象の隣へ配り直した —
  行ヘッダに「装備 + アビリティ + 称号」「エンチャント + シエナのオーラ」を 2 段目として置き、
  テシスコアは「入りません」と文章で言わず**値の無い 3 行目**(破線 + `?`)にして、
  合流先と最大値はその下の 1 行(押すとテシスコアのペインへ移る)に出す。
  残った注記は「2 行に分かれている理由 = 攻撃力(A)で別々の係数が掛かる」だけにした。
  このとき、旧注記が **強化倍率 +20% を「強化」行の隣に置いていた**のが誤読の元だと分かった。
  `attack_power_breakdown` は `equipment_attack = base + enhanced` に掛けるので、
  倍率は**両方の合計**に掛かる。「強化能力値」と「装備攻撃力強化倍率」が
  たまたま同じ「強化」という語を共有しているだけなので、注記でそこを明示的に切り離した

  攻撃補正だけ**(極・連なら突き/斬りの 2 列)にし、残りは部位詳細と同じ形のトグルで足す。
