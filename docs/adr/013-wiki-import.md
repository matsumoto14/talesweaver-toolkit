# ADR-013: Tale Wiki の取り込み

- ステータス: 採用
- 期間: 2026-09-02
- 関連 issue: #14 構想、#15 境界、#16 app-api、#17 索引、#18 AI 相談、#28 段階 0〜2
- 改訂: 2026-09-18 本文を持たない方針を確定(下の「本文は持たない」)。許諾打診の issue #29 はクローズ
- 改訂: 2026-09-20 段階 0 の取得と保存を実装。実測で差分の出どころを RSS から RecentChanges に変え、
  ページ数と置き場所を直した(下の「取得の実装(2026-09-20)」)

## 背景

ゲーム仕様の一次ソースは Tale Wiki(EUC-JP の PukiWiki、3,438 ページ)。これまでは必要なページを
手作業のスクリプトで 1 本ずつ取り込んでおり、装備カタログ・称号・ランダム OP などは穴が多く、
神鳥の聖物・クラウン・カードなどは自由入力のまま(ux-guidelines 原則 1 に反する)。
wiki を丸ごと取り込む土台を作り、その上に既存の取込を載せ替える。

計測(2026-09-02、ページ数は 2026-09-20 に訂正): ページ数 3,438、うちドメイン外(Quest / Event / NPC /
Shop / コメント等)約 1,500。ソース総量 約 15 MB(2026-09-20 実測。以前の「34 MB」は 25 ページの平均からの外挿)、取得 0.14 秒 / ページで全件 9 分。

## 決定

### ゴール(4 つ)

1. **AI に聞ける**(#18): 「あのクエどう進める」に出典付きで答える。根拠は取り込んだ wiki だけ
2. **登録で選べる物を増やす**: 装備・神鳥・クラウン・ペット・カード等をカタログ化して自由入力をなくす
3. **キャラに紐づけた案内**: 登録キャラの Lv・装備・進行から「次に行けるクエ / ダンジョン」を出す
4. **見やすい要約**: 見出し・表・要約をアプリ内で整形して読める。本文そのものは出さず、**元ページへの出典リンクを必ず付ける**

### 層

```
talewiki ──fetch──▶ [1] 取込キャッシュ(page, source, mtime, status)
                          │
            ┌─────────────┼──────────────────┐
            ▼             ▼                  ▼
   [2] 構造化抽出    [3] 索引(全文 + 意味)   [4] 見出し・表・要約
   gamedata の      サーバー。#17           ゴール 4。出典リンク付き
   Rust リテラル    ゴール 1 の根拠        (本文の全文は出さない)
   ゴール 2・3
```

- [1] は派生データの正本。gamedata の数値は [2] が [1] から生成する(手作業スクリプトを置き換える)。
  domain の正本はこれまでどおり gamedata / SQLite で、索引に置き換えない
- [2] だけがこのリポの中で完結する。[3][4] はサーバー(#15 の境界、#16 の基盤)を要る。[1] はサーバーに置かず、取込側(開発機)に留める
- [1] の置き場はリポ外の SQLite(既定 `%LOCALAPPDATA%\tw-context-wiki\wiki.sqlite`、`TW_WIKI_CACHE` で変えられる)。
  差分は RecentChanges + `?cmd=list` の全件突き合わせ(改名・削除の検出)
- 取得の実装は `tools/gamedata/wiki/talewiki.py` が正本。`.claude/skills/talewiki-fetch/scripts/fetch_page.py`
  は 1 枚だけ見たいとき用にそれを呼ぶ薄い口で、復号を二重に持たない

### 取得の実装(2026-09-20)

段階 0 の前半(取得とキャッシュ)を `tools/gamedata/wiki/`(`talewiki.py` / `store.py` / `sync.py`)として実装した。
実測で 2026-09-02 の前提が 3 つ外れていたので、次のとおり決め直す。

- **差分の出どころは RecentChanges。`?cmd=rss` は使わない。** RSS は 15 件(約 2 日分)しか返さず、
  週 1 の同期では取りこぼす。RecentChanges のソースは同じ更新日時を約 500 件持ち 2024-01 まで遡れる
- **`?cmd=list` の href は空白を `+` にする。** `Chapter/Secret+Chapter` の実名は `Chapter/Secret Chapter` で、
  `+` のまま `?cmd=source` に投げると `<pre>` が返らない。空白を含むページが 66 件あるので `unquote_plus` で戻す
- **ページ数は 3,438。** body 内の href は 3,443 個だが、ナビ 4 個と重複 1 個を含む(以前の「3,443」はこれを数えていた)
- **`?cmd=list` に載らない生きたページがある**。`FrontPage` が実際に載らない。だから一覧に無いだけで
  消えたとは決めず、取得で確かめて `<pre>` が返らないときだけ `gone` にする。取込対象は
  一覧 + RecentChanges の和で、本文があるページは **3,439**(一覧 3,438 + `FrontPage`)
- **RecentChanges には wiki 側が壊れた名前で記録した行がある**(`???á?ó?È/1LineBBS`、2024-11-15)。
  こういう `missing` / `gone` は mtime が動くまで取りに行かない(毎回失敗し続けるため)
- **ソース総量は約 15 MB**(SQLite のファイルは約 27 MB)。計画の「34 MB」は 25 ページの平均 10 KB からの
  外挿で、実際の平均は 4.4 KB だった

削除・改名は RecentChanges に出ないので `--full` の突き合わせでしか分からない。消えたページは
`status = 'gone'` にして**本文は残す**(改名なら新しい名前で入り直すため)。取得失敗もページ単位で記録し、
`source` は最後に成功した版のままにして全体を止めない。

全件取得の実績(2026-09-20): 3,439 ページ・失敗 1(上の壊れた名前だけ)・約 9 分。

置き場所は素の SQLite で拡張を使わない。**この先アプリ側がサーバー上で完結する形に移るとき、
Cloudflare D1 は SQLite なのでこのスキーマがそのまま載る**(ユーザー方針 2026-09-20)。
そのため今は抽象化層を挟まず、置き場所だけ環境変数で差し替えられるようにしてある。

### 本文は持たない

talewiki にライセンス表記が無い(2026-09-02 確認)。そこで**本文そのものをどこにも置かない**形に寄せる。
アプリが出すのは wiki から抽出した数値・構造と、見出し・表・要約、そして元ページへのリンクで、
本文の閲覧は常に元ページで行う。これは再配布ではないので、管理者への許諾を前提にしない
(打診の issue #29 は 2026-09-18 にクローズ)。

- サーバー(段階 3)は検索の索引と、回答に引用する見出し + 数行の断片までを持つ
- 段階 5 の表示も見出し・表・要約までで、本文の全文を整形して見せることはしない
- ゴール 2・3(数値・構造の抽出)はもともと該当しない

## 却下した選択肢

- 全文ミラー(許諾の有無を問わず): 却下。本文を持たない方針から外れる。読みやすさは見出し・表・要約で出す
- 索引をドメインの正本にする: 却下。計算の正本は gamedata / SQLite のまま(#17)
- 添付ファイルの丸ごと保存: 却下。画像はスキル・装備アイコンなど gamedata が使う分だけ
- コメント・wiki 編集・MenuBar 類の抽出: 却下。索引には入れるが抽出・案内には使わない

## 対象外

- 段階 3 以降のサーバー設計(#15 で決める)
