# UX/UI ガイドライン

UI を実装・変更するときに必ず参照する判断基準。目的は見た目の統一ではなく、**機能追加のたびに安易なフォーム羅列や情報過多な画面が生まれるのを防ぐ**こと。
具体的なコンポーネント構成・カラム数・フォルダ構成はここでは定めない(実装の現状は docs/architecture.md、視覚トークンは docs/design/Main.dc.html と `apps/desktop/src/app.css`)。

このツールのユーザーは「自分のキャラで、いま何ができるか・どう強くなれるか」を知りたいプレイヤーであり、データ入力をしたい人ではない。すべての原則はここから導かれる。

## 原則 1. 既知の情報をユーザーに入力させない

wiki・マスタデータ・登録済みキャラから取得または推定できる値は、原則として自動設定する。

- 固定値や通常変更しない値を、常時編集可能な入力欄として並べない
- 変更の必要性が低い値は **デフォルト値を持ち、通常は値として表示し、必要なときだけ編集できる** 設計を優先する
- 「柔軟性のために全部入力欄にする」設計は禁止。柔軟性は「上書きできる」ことで確保し、「毎回入力する」ことで確保しない
- 値が取れない・古い可能性があるなら、入力欄を増やすのではなく静的データ(gamedata)を充実させる。入力欄の追加は「データが無い」ことの暫定対応であり、その旨を docs/claude/decisions.md に `[仮]` で残す

**理由**: 旧リポジトリ(docs/legacy-twtoolkit.md)は素ステ・装備・約 60 項目のバフをセッションごとに手入力させる設計で、使うたびに同じ数値を打ち直す道具になった。入力欄は「自由度」ではなく「ユーザーが覚えて再入力しなければならない負債」である。

**判断の問い**: この値はどこから来るか? wiki / マスタ / 登録キャラ / 前回の選択 のいずれかで埋まるなら、入力欄にしない。

## 原則 2. 情報量が多いときは、削るのではなく構造化する

項目が多い場合に、すべてを同じ重要度・同じ UI で縦に並べない。

- 意味・用途・操作頻度でグルーピングし、「よく使う」「判断に必要」「詳細設定」「通常は変更しない」のように強弱を付ける
- 既定では要点だけが見え、詳細は展開・別領域・別画面で到達できるようにする(情報を消すのではなく、到達経路を階層化する)
- 数値の羅列は、読む側の問いに答える形に整える。「全中間値を出す」ことと「全部を同じ大きさで並べる」ことは別
- 減らす対象は**情報量ではなく認知負荷**。根拠(トレース・出典)は常に到達可能であること

**理由**: ダメージ計算は約 30 カテゴリ、ステ補正は 5 レイヤー×複数の補正源を持ち、正しく作るほど項目は増える。項目数を理由に情報を捨てると検証不能になり(旧リポの「最終値だけ一致」問題)、構造化せずに並べると誰も読まない。

**判断の問い**: この画面でユーザーが最初に答えを得たい問いは何か? その答えが一目で見えるか? 残りは「必要なら開ける」位置にあるか?

## 原則 3. 作成と詳細設定を分離する

新規登録時に、将来変更できる詳細項目をすべて入力させない。

- 「そのエンティティとして成立する最低限の情報」でまず登録できるようにする。キャラクターなら名前とキャラ種(+あれば素ステ)で成立する
- ステータス・覚醒・装備・ペット・ルーン・バフなどの詳細は、登録後に**十分な表示領域を使って**編集する。狭い登録フォームに設定項目を詰め込まない
- 詳細設定は原則 2 に従ってグループごとに分け、未設定のグループは「未設定(中立値で計算)」と分かるようにする
- 登録直後でも計算・提案が(中立値で)動くこと。詳細を埋めるほど精度が上がる、という漸進的な体験にする

**理由**: 詳細項目は今後も増え続ける(装備・属性・モンスターカード・称号…)。登録フォームに積むと、増えるたびに登録のハードルが上がり、最初の一歩が重くなる。「まず登録して、あとから育てる」形なら項目が増えても入口は変わらない。

**判断の問い**: この項目が空でも登録は成立するか? 成立するなら登録フォームではなく詳細設定に置く。

## 原則 4. 通常操作は「入力」より「選択」を優先する

計算・シミュレーション・提案は、登録済みキャラクター・スキル・敵・バフ・装備などの既知データを**組み合わせて選ぶ**ことで完結させる。

- 毎回同じ数値を再入力させない。前回の選択は既定値として引き継ぐ
- 画面上の入力欄は「キャラデータからの自動値を上書きする例外操作」として設計し、初期値は常に埋まっている
- ただし自由入力を禁止するのではない。次のものには自由入力を許可する:
  - シミュレーション用途の一時的な調整値(「もしステが +50 なら」)
  - 外部データから取得できない値(個人差のあるバフ量、シーズンで変わる値)
- 自由入力は「通常の選択」と見分けがつく形で置き(例外・調整であることが分かる)、可能な範囲(上限・下限)はデータ側で定義する

**理由**: 通常操作が選択で完結すれば、ユーザーは数値を覚えなくてよく、静的データの更新がそのまま全ユーザーの精度向上になる。自由入力を完全に禁止すると検証や未収録データへの対応ができなくなるので、「例外として許す」位置づけにする。

**判断の問い**: ユーザーはこの値を「知っている」のか「決めたい」のか? 知っているだけなら選択(または自動)、決めたいなら調整値として自由入力。

## 原則の適用順

衝突したら次の順で判断する。

1. 入力させない(原則 1)— まず値の出どころを探す
2. 選択にする(原則 4)— 出どころがあるなら選ばせる
3. 分離する(原則 3)— 登録の入口から外せるか
4. 構造化する(原則 2)— それでも多いなら強弱を付ける

「とりあえず入力欄を足す」はこの 4 段をすべて飛ばす行為であり、採らない。

## 新しい画面・項目を追加するときのチェック

- [ ] 追加する値の出どころ(wiki / マスタ / 登録キャラ / ユーザーの判断)を明示したか
- [ ] 出どころがあるものを入力欄にしていないか
- [ ] 登録フォームに「空でも成立する項目」を足していないか
- [ ] 画面の最初の問いと答えが明確で、詳細は開ける位置にあるか
- [ ] 自由入力は例外・調整として区別され、範囲がデータで定義されているか
- [ ] 根拠(トレース・出典)に到達できるか
