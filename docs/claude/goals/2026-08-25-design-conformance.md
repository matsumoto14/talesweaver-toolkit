# Goal: UI をデザインシステムに適合させる(適合するまでループ)

状態: **進行中(2026-08-25 開始。9 周目で §05 の違反 7 件。連続 0 はまだ)**

## 目的

docs/design-system.html を正として、**アプリ全体がそれに適合するまで「監査 → 修正 → 再監査」を繰り返す**。

これは指摘リストを消化する goal ではない。**終了条件を満たすまで周回する goal** で、
1 周ごとに全画面を見直す。個別の修正項目は周を回す中で出てくるものであって、あらかじめ列挙しない
(列挙すると、列挙から漏れたものが永久に直らない)。

デザインシステムは 2026-08-25 に新設したばかりで、**実装のほうが先に存在している**。
つまり適合していない箇所が必ずある。それを 1 周目で全部見つけられるとも限らないので、ループにする。

さらに、規格を書いている間にも main 側で実装が進んだ(段階 5〜7 + アンリーシュ / モンスターカード /
シエナ S18)。**規格と実装は並行して動く**という前提でループを設計してある — 1 周終えるたびに
main の変化も監査範囲に入る。

## 終了条件

次の 3 つを**同時に**満たしたら完了。

1. 監査チェックリストの全項目が、**全画面で違反 0**
2. 残っている非適合が、すべて design-system.html §14「これから作る画面の決定」に登録済みで、
   着手条件(ドメイン待ちなど)が明記されている
3. **2 周連続で新規違反 0**。1 周だけの 0 は「見落とした 0」と区別が付かないので信用しない

## 1 周の手順

```
① 監査  → ② 分類  → ③ 修正  → ④ 記録  → ⑤ 次の周へ
```

### ① 監査

下のチェックリストで**全画面**を見る。機械監査(A)はスクリプト、実機監査(B・C)は `gui-smoke` skill。
「前の周で見たから」で飛ばさない — 修正が別の違反を生むことがある。

### ② 分類

検出したものを 3 つに分ける。**ここが一番大事な工程**で、機械的に実装を直すのは誤り。

| 分類 | 意味 | 対応 |
|---|---|---|
| **違反** | 規格が正しく、実装が間違っている | 実装を直す |
| **規格の穴** | 実装のほうが正しく、規格が雑・言い過ぎ・言い足りない | **design-system.html を直す** |
| **決定待ち** | どちらが正しいか、この場では決められない | §14 に登録して次の周へ持ち越す |

**規格側が間違っていることは実際にある。** v4 の密度(11px 見出し・9px ラベル)のように、
実装のほうが意識的な判断で、規格が後から雑に書かれた可能性を常に疑う。
実装を規格に合わせて 1 画面の情報量が減ったら、それは適合ではなく劣化。判断はメインセッションがする。

### ③ 修正

- 「違反」を直す。1 周で全部直らなくてよい。**直した分だけ commit して次の周へ**
- 「規格の穴」はデザインシステム側を直す。こちらも同じ扱いで commit する
- 実機で 3 タブとも崩れがないことを確認する(`gui-smoke`)

### ④ 記録

下の「周ごとの記録」に 1 行足す。**見送ったものは理由込みで書く** — 理由が無い見送りは次の周で必ず蒸し返す。

- **§09 規則 5 — 押した候補が一覧から消える。***理由*: 規則 5 は「消えることを動きで見せる」を
  求めているが、**§10 に「行が消える」型が無い**。型を足すのか、消さずに「適用中」として残すのかは
  規格の判断。**§14 に保留 D として登録**した。いまは右カラムのチップ列で行き先を追える

**残っている保留(§14「判断を保留しているもの」)**

A. スライダーは §07 の 5 形態のどれなのか / B. オン・オフがチェックボックスとチップに割れている /
C. 上限到達を金で言うか紫で言うか / D. 押した候補が消えるのをどう見せるか。
いずれも **v4 の実物を見ないと決められない**ので、決めるまで違反として数えない。

### 3 周目の詳細

2 周目で足したもの(鎖・棚卸し・収録度・お気に入り・§10)が別の違反を生んでいないかを見た。
**座標を実測する**方法を使った — 値の桁を変えて、隣の要素の x が動くかを Playwright で測る。

**違反(実装を直した)**

1. §01 — 補正源の ★ が行カードの外に独立した枠を持っていて、1 行に面が 2 枚あった。
   ホームタブは行カードの中に ★ を置いているので、形も割れていた。行の中に入れた
2. §09 規則 4 — 「いまの実力」の最終能力値が flex + 折り返しで、HACK を 215 → 1,424 に
   すると隣の INT が 12px ずれた。列を grid で固定(3 列)して、密度を保ったまま止めた。
   実測: 修正前 `[103,173,233,…]` → `[103,177,251,…]`、修正後は不変
3. §13 — 2 周目で足した「効いていない分」が状態の名前で、問いになっていなかった。
   「どこで頭打ち?」に直した

**確認して問題なかったもの**

- §09 規則 4 — 鎖の各段(x 不変)、装備値テーブル(td の中身を 6 桁に差し替えて列が動かないことを確認)
- §02 — 意味のある帯は 金 1 / ラベンダー 1 で 2 種以内
- §01 — 棚卸し表はインセット面 `rgb(193,211,230)` に載っている
- §13 の「3 つの『無い』を書き分ける」— 収録度バッジ(判定中 / 敵データなし / スキル未収録)と

### 4 周目の詳細

**違反(実装を直した)**

§10 規則 2「同時に 2 箇所が変わったら、2 箇所とも動かす」— 同じ値が 2 箇所に**同時に見えて**
いるのに、片方にしか跳ねが付いていなかった。

1. 「いまの実力」のサマリー行(常時見える)と 最終能力値カード(開いたとき)
2. 補正源リスト下の「いまの攻撃力」フッターと 「攻撃力(A)」カード

**確認して問題なかったもの(実測)**

- §09 規則 1 — 対象ポップオーバーのトリガ `[125,178] → [125,178]`、「なぜこの数字?」の

### 5 周目の詳細

**新規違反 0。**(終了条件 3 の 1 周目)

実測した結果:

| 観点 | ホーム | 計算 | キャラ |
|---|---|---|---|
| §06 アイコンの単独表示(名前なし) | 0 | 0 | 0 |
| §05 数値が等幅 + tabular-nums でない | 0 | 0 | 0 |
| §00「—」で欠けを見せている数 | 18 | 0 | 0 |
| §00「0」表示 | 2 | 2 | 15(装備値テーブルの実データ) |

「0」表示はすべて**実際に 0 の値**(未装備部位の装備値など)で、未収録・未設定を 0 で
埋めている箇所は無かった。

**規格の穴(design-system.html を直した)**

§03 は「斜線は一貫して『効いていない・持っていかれた』の記号」と言い切っているが、
§06 のアイコンのプレースホルダも同じ 135° の縞。規格の中で同じ模様に意味が 2 つある。
§03 に但し書きを足した — プレースホルダは同系色 2 色の薄い縞で値の上には出ない。
**濃い 2 色の斜線が量の上に重なっていたら、それは常に「効いていない量」**。

**§01 について確認したこと** — 「攻撃力(A)」の値やヒーロー数値は白い面の上にあるが、
§01 が禁じているのは「読み取り専用の数値を(入力欄に見える)**白い箱に入れる**」こと。
裸のテキストとして置く分には違反ではない。表・一覧の読み取り専用の数値
(最終能力値 / 装備値 / 棚卸し)はすべてインセット面に載っている。

### 6 周目の詳細

**違反(実装を直した)— §07「このシステムで一番拘っているところ」**

素の `<select>` とチェックボックスは **5 形態のどれでもなかった**。形態 2 は
「段階そのものを見せる。『3』という数字を打たせない」でモックはセグメント、
形態 3 は「値はチップの中に書く。選ぶ = 値が確定する」。

1. `src/ui/StepSelect.svelte` を追加し、順序があって並べられる有限選択を段階選択にした
   (覚醒段階 / ランダムOP のランク / ペット S スキル / シエナの増幅段階 /
   アンリーシュの Lv / オーグメント / レインフォース / ストロングウェポン / 強化 Lv)
2. オン・オフのチェックボックスをチップにした。値をチップの中に書き、縦 1 列だったものを
   横並びにしたので密度も上がった

**見た目は規格の `.seg` / `.chip` に合わせる。**最初に自作の見た目(離れた pill)で
書いてしまい、指摘を受けて直した。規格は「1 つの枠の中にボタンが並び、間は弱い区切り線
1 本、選択中は水色のグラデ」。**規格には実物の CSS がある**ので、新しい部品を作るときは
先にそれを見る。

**確認して問題なかったもの(全画面で機械測定)**

計算タブ 4 状態(攻撃 / なぜこの数字 / トレース / 防御)、補正源 17 ペイン、
レール折りたたみ、ホーム — §04 角丸が 4 段の外 0 件、§05 数値書体 NG 0 件、
§06 アイコン単独表示 0 件、§10 0.5s 超の動き 0 件。

**保留に E を追加**

順序のある有限選択は段階選択にできたが、**順序のない有限選択**(属性 / 対象ステ /
アビリティ / キャラ)と**段階として並べられない長さ**(エタの意志 Lv 0〜100)は
5 形態に当てるものが無い。ドロップダウンは 5 形態のどこにも無い。

### 7 周目の詳細

**§08「部品」は寸法まで書いてある実物の節**だと気づいて、そこと突き合わせた周。

**違反(実装を直した)**

1. §07「範囲は入力欄が知っている。値の隣に常設し、範囲外を打てなくするのではなく
   範囲を見せる」— `StatInput` は 22 箇所で使っているのに、範囲を出していたのは 3 箇所だけ
   だった。`capGauge` を既定 true にした。下限が 0 でない入力(調整の ±999)は
   「値 / 上限」ではなく範囲そのものを出す
2. §08「フィールド — 表示が既定・編集は例外」— 実装は常に入力欄が出ていて、1 画面が
   入力欄の列になっていた。**初期値は常に埋まっているので、ふだんは読み取り表示**
   (インセット面)にし、押したときだけ入力欄 + スライダー + MAX + 範囲を出す。
   フォーカスが部品の外へ出たら戻る。「適用」は挟まない
3. §08 の寸法ずれ — スプリッターの当たり判定 6px → 9px、hover の面が濃すぎ(規約は
   「ごく薄い面」)、title が無い、主要ボタンの inset ハイライトが無い

**この周で分かったこと** — §08 は「すべて実物。触れる」と書いてあるとおり、
**寸法と状態が具体的に決まっている節**。新しい部品を作るときも、既存の部品を直すときも、
まずここと突き合わせる。6 周目の「自作の見た目で書いてしまった」と同じ根の見落とし。

### 8 周目の詳細

**§11・§12「組み上がり」は、規格を全部使うとどうなるかの実物**。1 枚の画面として
何が出ているべきかが書いてある。突き合わせた。

**違反(実装を直した)**

1. §11「素ステ → 最終を **1 本のバー**で見せる。数字の羅列ではなく『どれだけ伸びたか』が
   一目で分かることを狙っている」— 実装は数字の表だけだった。能力値の表に
   「素ステ → 最終」列を足した(灰 = 素ステ、青 = 補正で乗った分、長さは上限に対する割合)
2. §11 / §09 規則 4「『満』バッジの枠を常に確保してあるので、出ても行がずれない」—
   条件表示だった。枠を確保し、色も赤茶から金(= 上限。§03 予約色)に直した
3. §12「届いたら面の色が変わる」「枠は値の有無で伸び縮みしない」— 上限に届いた入力欄の
   面を金にした。部位一覧の強化バッジ・シエナの段階バッジの枠を確保した

**確認して問題なかったもの**

- §11「5 レイヤーの内訳(どのバフがどのレイヤーに入ったか)」— 「補正の内訳」の層列で
  既に満たしていた
- §12「装備品の候補は値を添えて並べる」— アイテム一覧に突き / 斬りのレンジが出ている
- §12「自由入力がこの画面に 1 つも無い」— 残っているのは検索欄だけで、値を決める入力ではない

**保留に F を追加**

§12 は装備ペインの下に 4 数値の帯(突き合計 / 斬り合計 / 追加固定 / A 攻撃力)を置く形だが、
実装は**画面共通のフッター「いまの実力」**がその役をしている。専用の帯を足すと同じ値が
2 箇所に出る。§12 の意図(押した瞬間に下で動く)は共通フッターでも満たせているので、
**規格側を実装に寄せる**可能性が高い。

### 9 周目の詳細

寸法を実測した周。**規格には寸法が具体的に書いてある**(帯の高さ・実寸のスケール・面の色)ので、
そこと突き合わせた。

**違反(実装を直した)** — §05 の実寸スケールの外にあった font-size を寄せた

| 直した場所 | 前 | 後 | 根拠 |
|---|---|---|---|
| ホーム右カラムの選択中 | 34px | 40px | §05「44 / 40 / 27 = 主役 / 右カラムの選択中 / サマリー」 |
| 攻撃力(A)の値・いまの攻撃力 | 20 / 22px | 19px | カード群の親 |

| ▼・小バッジ | 8px | 8.5px | 最小段 |

**規格の穴(design-system.html を直した)**

§05 の実寸スケールに **10** が抜けていた。実装はセクションラベル・カラム帯の注記・
部位名などで 10px を広く使っている。列挙に足した。

**機械監査に R10 を追加** — `font-size` が実寸スケールの外にあるものを検出する。
実機で見つけたものを次の周からはスクリプトが拾う。実際、実測では見えていなかった
1 件(主軸スキル未選択で非表示だった 22px)を R10 が拾った。

**確認して問題なかったもの(実測)**

§02 アプリ帯 52px / カラム見出し 30px(規格どおり)、§01 の面 3 層も規格の色そのまま
(地 `rgb(201,216,238)` / カード白 / インセット `rgb(193,211,230)`)。

## やらないこと

- **規格に合わせるために 1 画面の情報量を減らすこと。**密度は v4 が意識的に選んだもので、
  規格のほうが後から書かれている。減らす判断が要るなら、それは別の goal
- **機械監査の候補を一括置換すること。**②の分類を飛ばした修正は、規格の穴を実装に押し付ける
- **§14 のドメイン待ち項目を先取りして作ること。**着手条件が満たされるまで待つ
