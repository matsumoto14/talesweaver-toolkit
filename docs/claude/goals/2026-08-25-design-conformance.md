# Goal: UI をデザインシステムに適合させる(適合するまでループ)

状態: **進行中(2026-08-25 開始。1 周目終了、2 周目へ)**

## 目的

docs/design-system.html を正として、**アプリ全体がそれに適合するまで「監査 → 修正 → 再監査」を繰り返す**。

これは指摘リストを消化する goal ではない。**終了条件を満たすまで周回する goal** で、
1 周ごとに全画面を見直す。個別の修正項目は周を回す中で出てくるものであって、あらかじめ列挙しない
(列挙すると、列挙から漏れたものが永久に直らない)。

デザインシステムは 2026-08-25 に新設したばかりで、**実装のほうが先に存在している**。
つまり適合していない箇所が必ずある。それを 1 周目で全部見つけられるとも限らないので、ループにする。

さらに、規格を書いている間にも main 側で実装が進んだ(段階 5〜7 + アンリーシュ / モンスターカード /
シエナ S18)。**規格と実装は並行して動く**という前提でループを設計してある — 1 周終えるたびに
main の変化も監査範囲に入る。

## 終了条件

次の 3 つを**同時に**満たしたら完了。

1. 監査チェックリストの全項目が、**全画面で違反 0**
2. 残っている非適合が、すべて design-system.html §14「これから作る画面の決定」に登録済みで、
   着手条件(ドメイン待ちなど)が明記されている
3. **2 周連続で新規違反 0**。1 周だけの 0 は「見落とした 0」と区別が付かないので信用しない

## 1 周の手順

```
① 監査  → ② 分類  → ③ 修正  → ④ 記録  → ⑤ 次の周へ
```

### ① 監査

下のチェックリストで**全画面**を見る。機械監査(A)はスクリプト、実機監査(B・C)は `gui-smoke` skill。
「前の周で見たから」で飛ばさない — 修正が別の違反を生むことがある。

### ② 分類

検出したものを 3 つに分ける。**ここが一番大事な工程**で、機械的に実装を直すのは誤り。

| 分類 | 意味 | 対応 |
|---|---|---|
| **違反** | 規格が正しく、実装が間違っている | 実装を直す |
| **規格の穴** | 実装のほうが正しく、規格が雑・言い過ぎ・言い足りない | **design-system.html を直す** |
| **決定待ち** | どちらが正しいか、この場では決められない | §14 に登録して次の周へ持ち越す |

**規格側が間違っていることは実際にある。** v4 の密度(11px 見出し・9px ラベル)のように、
実装のほうが意識的な判断で、規格が後から雑に書かれた可能性を常に疑う。
実装を規格に合わせて 1 画面の情報量が減ったら、それは適合ではなく劣化。判断はメインセッションがする。

### ③ 修正

- 「違反」を直す。1 周で全部直らなくてよい。**直した分だけ commit して次の周へ**
- 「規格の穴」はデザインシステム側を直す。こちらも同じ扱いで commit する
- 実機で 3 タブとも崩れがないことを確認する(`gui-smoke`)

### ④ 記録

下の「周ごとの記録」に 1 行足す。**見送ったものは理由込みで書く** — 理由が無い見送りは次の周で必ず蒸し返す。

## 監査チェックリスト

### A. 機械監査(スクリプトで検出する)

段階 0 で `tools/design-audit/` を用意し、以後の周で毎回走らせる。検出するのは次のもの。

- **直書きの色**で、`app.css` に同値のトークンが既にあるもの(`--accent` があるのに `#426DD6` と書いている等)
- **4 段以外の `border-radius`**(12 / 9 / 6 / 999 と `50%` 以外)
- **`--r-*` を使わない `border-radius` の直書き**
- **数値の表示で `tabular-nums` / `.num` が付いていない**もの(`font-num` を使っているのに `font-variant-numeric` が無い)
- **アイコンサイズが 20 / 28 / 40 / 64 以外**(`Icon.svelte` の型で縛れているが、CSS 側の上書きを検出する)
- **`transition` / `animation` の duration が 0.5s 超**
- **状態 6 系統の色を、6 系統以外の組み合わせで使っている**もの
- TS / Svelte に**色の実値が直書き**されているもの(`COST_COLORS` のように CSS 変数参照にできるはず)
- **枠や地を持つ操作部品に `border-radius` の宣言が無い**もの(§04 は 0 を段に数えない。1 周目で追加)

機械監査は**違反の候補**を出すだけで、判定はしない。②の分類にかける。
ルール一覧は `python tools/design-audit/run.py --list`。

**2026-08-25 更新** — remaining-sources の段階 5〜7(中ディレイ / DPS・能力値上限・クリティカル率)が

## 段階 0 — 監査スクリプトを用意する(1 回だけ) — **完了(2026-08-25)**

### 1 周目の詳細

**違反(実装を直した)**

1. §03/§15 — 状態の 6 系統が CalcPage / HomePage に hex で重複定義。`app.css` の `--state-*` +
   `src/ui/states.ts` に集約(色は不変)
2. §15 — トークンと同値の hex 直書き 113 箇所を `var(--…)` に
3. §03 — 到達を表す点(ホームの `entry-dot` / 計算タブの候補ドット)が 6 系統の外の色だった
4. §03 — 「攻撃力をつくる」の内訳で共通スキル(PW / SW)由来の帯にラベンダー(`--sim`)を使っていた。
   共通スキルはキャラに保存されるデータなので予約色の誤用。`--flow-2` へ
5. §03 — 上限到達の「満」バッジが赤茶(`--danger`)だった。上限に届くことは危険ではない。金へ
6. §05 — `input[type=number|text]` と `.stage-no` に `tabular-nums` が無い / ◀▶▼ の記号に数値書体
7. §04 — `select` / 数値欄 / MAX / チェックボックス / スライダーに角丸が無い(0 は 4 段に入らない)
8. §00/§09 — 「足りない分をどう埋める?」が候補 0 件でパネルごと消え、カラム帯の常設リンクが
   指す先を失っていた。0 件でも枠を残し、「候補が無い」のか「超えるものが無い」のかを書き分ける

**規格の穴(design-system.html を直した)**

1. §03 — 文字色 6 段のうち 3 段、予約色の金・敵の赤茶・緑の明にトークンが無かった
   (`--fg-head` / `--fg-sub` / `--fg-off` / `--gold` / `--mob` / `--good-soft`)
2. §03 — 積み上げ帯・流れ帯の「内訳の色」は 6 系統でも予約色でもないのに居場所が無かった。
   「内訳の色」節を新設(`--flow-*`)
3. §03 — コストの色が実装に無いタグ(育成 / 周回 / 素材・課金)を並べていた。実装の 3 タグへ
4. §15 — 対応表の「状態の 6 系統 → `BADGE_*`」が実態と合わなくなった

**決定待ち(design-system.html §14「判断を保留しているもの」に登録)**

- A. 数値入力のスライダーが §07 の 5 形態のどれでもない
- B. オン / オフの選択がチェックボックスとチップに割れている
- C. 上限到達を金で言うか紫で言うか(§03 と §07 が文書内で食い違っている)

**見送り(理由込み)**

- **§09 違反 — 装備の部位詳細がドリルダウンではなく置き換えになっている。**部位行を押すと
  部位一覧が消えてアイテム選択に入れ替わり、「‹ 装備一覧へ」で戻る形。規格は「右にペインを増やす」。
  *理由*: 3 ペイン化は Splitter の配分とスクロール器の作り直しを伴い、1 周目の色トークン化と
  同じ commit に混ぜると視覚回帰の切り分けができない。**2 周目で単独の変更として扱う**
- **§00 — 補正源ペインの wiki 解説文が長く、触らない場所が畳まれていない**(クリティカル率で 6 行)。
  *理由*: 畳むと初見で式が読めなくなる可能性があり、ux-guidelines 側の判断が要る。2 周目で判断する
- **§14 決定 1〜3・5・6 — 未着手のまま。***理由*: 1 周目は機械監査の一掃と実機の一巡に充てた。
  決定 1(鎖)は計算タブのレイアウト変更なので、§09 の 3 ペイン化と同じ周でまとめる
- **機械監査の穴 — 「border-radius の宣言が無い」を検出していなかった。***理由ではなく対応*:
  1 周目中に R9 として追加済み(検出 → 修正まで完了)

## やらないこと

- **規格に合わせるために 1 画面の情報量を減らすこと。**密度は v4 が意識的に選んだもので、
  規格のほうが後から書かれている。減らす判断が要るなら、それは別の goal

- **§14 のドメイン待ち項目を先取りして作ること。**着手条件が満たされるまで待つ
