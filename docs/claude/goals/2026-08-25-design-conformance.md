# Goal: UI をデザインシステムに適合させる(適合するまでループ)

状態: **進行中(2026-08-25 開始)**

## 目的

docs/design-system.html を正として、**アプリ全体がそれに適合するまで「監査 → 修正 → 再監査」を繰り返す**。

これは指摘リストを消化する goal ではない。**終了条件を満たすまで周回する goal** で、
1 周ごとに全画面を見直す。個別の修正項目は周を回す中で出てくるものであって、あらかじめ列挙しない
(列挙すると、列挙から漏れたものが永久に直らない)。

デザインシステムは 2026-08-25 に新設したばかりで、**実装のほうが先に存在している**。
つまり適合していない箇所が必ずある。それを 1 周目で全部見つけられるとも限らないので、ループにする。

## 終了条件

次の 3 つを**同時に**満たしたら完了。

1. 監査チェックリストの全項目が、**全画面で違反 0**
2. 残っている非適合が、すべて design-system.html §14「これから作る画面の決定」に登録済みで、
   着手条件(ドメイン待ちなど)が明記されている
3. **2 周連続で新規違反 0**。1 周だけの 0 は「見落とした 0」と区別が付かないので信用しない

## 1 周の手順

```
① 監査  → ② 分類  → ③ 修正  → ④ 記録  → ⑤ 次の周へ
```

### ① 監査

下のチェックリストで**全画面**を見る。機械監査(A)はスクリプト、実機監査(B・C)は `gui-smoke` skill。
「前の周で見たから」で飛ばさない — 修正が別の違反を生むことがある。

### ② 分類

検出したものを 3 つに分ける。**ここが一番大事な工程**で、機械的に実装を直すのは誤り。

| 分類 | 意味 | 対応 |
|---|---|---|
| **違反** | 規格が正しく、実装が間違っている | 実装を直す |
| **規格の穴** | 実装のほうが正しく、規格が雑・言い過ぎ・言い足りない | **design-system.html を直す** |
| **決定待ち** | どちらが正しいか、この場では決められない | §14 に登録して次の周へ持ち越す |

**規格側が間違っていることは実際にある。** v4 の密度(11px 見出し・9px ラベル)のように、
実装のほうが意識的な判断で、規格が後から雑に書かれた可能性を常に疑う。
実装を規格に合わせて 1 画面の情報量が減ったら、それは適合ではなく劣化。判断はメインセッションがする。

### ③ 修正

- 「違反」を直す。1 周で全部直らなくてよい。**直した分だけ commit して次の周へ**
- 「規格の穴」はデザインシステム側を直す。こちらも同じ扱いで commit する
- 実機で 3 タブとも崩れがないことを確認する(`gui-smoke`)

### ④ 記録

下の「周ごとの記録」に 1 行足す。**見送ったものは理由込みで書く** — 理由が無い見送りは次の周で必ず蒸し返す。

## 監査チェックリスト

### A. 機械監査(スクリプトで検出する)

段階 0 で `tools/design-audit/` を用意し、以後の周で毎回走らせる。検出するのは次のもの。

- **直書きの色**で、`app.css` に同値のトークンが既にあるもの(`--accent` があるのに `#426DD6` と書いている等)
- **4 段以外の `border-radius`**(12 / 9 / 6 / 999 と `50%` 以外)
- **`--r-*` を使わない `border-radius` の直書き**
- **数値の表示で `tabular-nums` / `.num` が付いていない**もの(`font-num` を使っているのに `font-variant-numeric` が無い)
- **アイコンサイズが 20 / 28 / 40 / 64 以外**(`Icon.svelte` の型で縛れているが、CSS 側の上書きを検出する)
- **`transition` / `animation` の duration が 0.5s 超**
- **状態 6 系統の色を、6 系統以外の組み合わせで使っている**もの
- TS / Svelte に**色の実値が直書き**されているもの(`COST_COLORS` のように CSS 変数参照にできるはず)

機械監査は**違反の候補**を出すだけで、判定はしない。②の分類にかける。

### B. 実機監査(画面を見て判断する)

対象画面(全部):

- 共通 — アプリ帯 / タブ / キャラレール / エラー帯
- ホーム — 到達一覧 / エリア折りたたみ / 右カラム(選択中・次に変えるなら)
- 計算タブ — 対象パネル / スキル選択 / ヒーロー数値 / 足りない分をどう埋める / なぜこの数字 / 防御タブ / トレース
- キャラタブ — 補正源一覧 / 各補正源ペイン(装備・恒常・バフ・キャラスキル・共通スキル・極限スキル・称号・ランダムOP・属性・シエナ・テシスコア・調整)/ 部位詳細 / 登録ペイン / いまの実力

見る観点(design-system.html の節に対応):

| # | 観点 | 落ちやすいところ |

### C. §14「これから作る画面の決定」の適合

design-system.html §14 に置いた決定も適合項目として扱う。**ドメイン待ちのものは「未着手」で違反にしない**が、
着手条件が満たされたら次の周から違反になる。

| # | 決定 | 着手条件 | 状態 |
|---|---|---|---|
| 1 | ダメージは「鎖」で出す(ゲートとレート) | remaining-sources 段階 5(中ディレイ) | ドメイン待ち |
| 2 | 効いていない分の棚卸しを 1 箇所に | なし(5 種のうち 3 種は実装済み) | **着手可** |
| 3 | 補正源リストを操作頻度で 3 群に | なし | **着手可** |
| 4 | 相手依存の値は 2 つに割る | なし(規約。段階 7 で守る) | 規約 |
| 5 | 欠けの表現を行内から行頭へ | なし | **着手可** |
| 6 | 試し変更は同時 3 件まで | なし | **着手可** |

各決定の中身は design-system.html §14 が正。ここには要約しか書かない(二重管理にしない)。

## 段階 0 — 監査スクリプトを用意する(1 回だけ)

ループを回せる状態にする。ここだけは周に含まれない前準備。

- `tools/design-audit/` に、A の機械監査を実行するスクリプトを置く。出力は「ファイル:行 / 検出したもの / 該当する規格の節」
- **判定はしない。候補を出すだけ。**閾値で自動修正しない(規格の穴を実装に押し付けることになる)
- 実行は `python tools/design-audit/run.py`。CI には入れない(判断が要るので、人が見る前提)

受け入れ条件: スクリプトが走って候補が出る / 1 周目の監査でそれを使う

## やらないこと

- **規格に合わせるために 1 画面の情報量を減らすこと。**密度は v4 が意識的に選んだもので、
  規格のほうが後から書かれている。減らす判断が要るなら、それは別の goal
- **機械監査の候補を一括置換すること。**②の分類を飛ばした修正は、規格の穴を実装に押し付ける
- **§14 のドメイン待ち項目を先取りして作ること。**着手条件が満たされるまで待つ
