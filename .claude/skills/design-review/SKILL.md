# デザインレビュー

正は **docs/design-system.html**(出典はデザインモック「TW Toolkit Prototype v4」= claude.ai/design プロジェクト「Repo UI mockup directions」。ファイルは git 履歴 docs/mock/ 参照。
食い違ったら v4 が正)。適合ループの決定記録は `docs/adr/006-ui-design-system.md`。

## 見るもの — §00「いつでも意識する 5 つ」

規格(§01〜§13)は**手段**で、目的はこの 5 つ。**規格に 100% 合っていても画面は悪くなる**ので、
規格チェックだけで終わらせない。

| # | 原則 | 自分に問う | 測り方 |
|---|---|---|---|
| 01 | 視線を動かさない | この欄を決めるまでに、目は何回動く? | `attention.js`(A1 折り返し / A2 横並び / A4 はみ出し / A5 高さのずれ) |
| 02 | 要らないものを見せない | いま出ているもののうち、今見なくていいものはどれ? | `attention.js` A3 が**数を出す**。要否は人が決める |
| 03 | 押した場所は動かない | 押したあと、いま押したものはまだそこにある? | `clickall.js`(押せる要素を総当たりし、前後の `offsetTop` を比べる) |
| 04 | 変わったら動かす | これを押して変わる場所は、全部動く? | `motion.js`(変わったのに跳ねなかったものを挙げる) |
| 05 | 考えさせない | ここでユーザーは、何かを覚えたり計算したりしている? | **機械では測れない。スクリーンショットで判断する** |

## ⓪ 変更ごとの自己チェック(毎回・30 秒)

1 画面直したら、出す前にこの 5 つを声に出して確かめる。**ここを飛ばした変更は、たいてい
「規格には合っているが安っぽい」ものになる。**

| # | 問い | 落としやすいところ |
|---|---|---|
| 01 | 目は何回動く? | 段の折り返し・欄の横並び・行ごとに違う幅 |
| 02 | 今見なくていいものはどれ? | ほぼ選ばれない選択肢(未装着・なし)が段を占めている |
| 03 | 押したものはまだそこにある? | 押すと言葉が変わるボタンの幅・入場の `scale`・後から出るスクロールバー |
| 04 | 変わる場所は全部動く? | **新しく足した数値・要約・バッジに `use:bump` / `use:flash` を付け忘れる** |
| 05 | 覚えたり計算したりしている? | 選択肢に結果(補正値・%)が乗っていない・単位や上限が隣にない |

見た目が「平たい箱」になっていないかも見る。**面はインセット + ハイライト、値は数値書体、
状態はバッジ**。面全体を状態色で塗るのは §02(意味のある帯は 1 画面 2 種まで)の枠を食う。

## ① 機械で測る

**A. ソースを読む**(アプリの起動は不要)。色・角丸・書体・寸法の 10 ルール:

```
python tools/design-audit/run.py
```

**B. 動いているアプリを測る**。`gui-smoke` skill の手順で起動(CDP 9222)してから:

```
NODE_PATH=/c/github/private/twtoolkit/node_modules node tools/design-audit/live/<name>.js
```

毎周走らせるのは `attention.js`(01・02)・`clickall.js`(03)・`motion.js`(04)・
`inputs.js`(§07 5 形態)・`surfaces.js`(§01 面)。
ほかの観点は `tools/design-audit/live/README.md` の表から選ぶ。

**出てきた数は候補であって違反ではない。**特に A3(見えている選択肢の数)は、
数だけ見て減らすと今度は情報が足りなくなる。判断は ② でする。

## ② スクリーンショットを撮って、ユーザーに判断してもらう

**02 と 05 は人が見ないと決まらない。**ここを飛ばして自分で決めない —
2026-08-26 の覚醒段階(0〜5 を幅いっぱいに並べた欄)は、機械監査 10 ルール 0 件・
こちらの目視でも見逃し、ユーザーの指摘で初めて出た。

1. `gui-smoke` で**変えた画面**と、A3 の多い画面(選択肢が多く出ている画面)を撮る
2. 撮った画像を **`SendUserFile` でユーザーに出す**。ファイルパスを書くだけにしない
3. 一緒に、その画面について**具体的に何を聞くのかを 1〜2 点だけ**書く
   (「テシスコアは常時 114 個の選択肢が出ている。段を畳むか」など)。
   「どうですか」と丸投げしない
4. ユーザーの判断を受けて ③ へ

## ③ 分類

| 分類 | 意味 | 対応 |
|---|---|---|
| **違反** | 規格・5 原則が正しく、実装が間違っている | 実装を直す |
| **規格の穴** | 実装のほうが正しく、規格が雑・言い過ぎ・言い足りない | `docs/design-system.html` を直す |
| **決定待ち** | どちらが正しいかこの場で決められない | §14 に着手条件込みで登録し、次の周へ |

- **規格側が間違っていることは実際にある。**v4 の密度(11px 見出し・9px ラベル)のように、
  実装が意識的な判断で規格が後から雑に書かれた可能性を疑う。迷ったら **v4 を開いて確かめる**
- **実装を規格に合わせて 1 画面の情報量が減ったら、それは適合ではなく劣化**

## ④ 直す

- **見た目の崩れを CSS で消さない。**折り返し・余白・ずれは 5 原則が崩れている**症状**で、
  幅や余白を調整すると「きれいに間違っている」状態になり、次から誰も気づけなくなる。
  直すのは**出す量と並び**のほう
- 見た目は **`app.css` の共通部品にだけ置く**(§08 の実演を写したもの)。
  ページの `<style>` に同じ見た目を書き直さない。無い形が要るなら共通部品側に足す
- 直したら ① の B をもう一度走らせる(修正が別の崩れを生む)
- 1 周で全部直らなくてよい。**直した分だけ commit** して次の周へ

## ⑤ 記録

`docs/adr/006-ui-design-system.md` の「経緯」に、方針が変わった点だけ 1 行足す(作業ログは書かない)。
**見送りは理由込みで書く** — 理由の無い見送りは次の周で蒸し返す。
終了条件は「全項目 0 + 残りは §14 に登録済み + **2 周連続で新規違反 0**」。

## 注意

- **監査は保存・削除・登録を押さない。**開発 DB を書き換えると、あとで実装のバグと区別が付かない
- **ビューポート座標で測らない。**`click()` は要素を視界に入れるためにスクロールする。
  `offsetLeft` / `offsetTop` で測り、押すのは `dispatchEvent("click")`
- 新しい観点を測りたくなったら、その場限りのスクリプトにせず `tools/design-audit/live/` に足して
  README の表に 1 行書く。次の周でも走る形にしないと、その観点は 1 回で消える
- 重い実行(起動・全画面の巡回・撮影)は `smoke-tester` に出してよい。
  **ただし ② の判断はユーザー、③ の分類はメインセッションがする。**Subagent に決めさせない
